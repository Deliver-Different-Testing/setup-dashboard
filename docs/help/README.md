# Setup Dashboard help centre

**Written 25 Oct 2026** against branch `feat/settings-rewrite` (the Settings/Routed Ops rewrite, owner Jacob).
Every rule quoted here is the one the code enforces (`Services/Steps/*Pusher.cs`, `Services/Steps/StepCatalog.cs`,
`Controllers/ImportController.cs`, `Models/SmartUpload.cs`). When the code changes, the article changes with it.

## Why these exist

Auto-Mate is the help system for the Setup Dashboard, and Auto-Mate is driven out of the Customer Success Platform
(`dfrntcrm`, "CSP"): its Knowledge Base, its Help Centre and the Ask Auto-Mate chat. The dashboard's own sidebar is
scripted text today (`ClientApp/src/data/chatMessages.ts`). These articles are the content that the CSP **shipped**
collection ("Deliver Different guides") needs so Auto-Mate can answer setup questions, and so a tenant preparing their own
data files knows exactly what each file must contain.

Two readers, both served by the same articles:

- **Tenant admins** doing their own setup or preparing exports from their old system.
- **DFRNT staff** sitting with a new tenant, who need the "DFRNT does this" checklist and the dead-ends on a brand-new tenant.

## Files

| Path | What |
|---|---|
| `README.md` | This file: contract, authoring rules, publishing. |
| `manifest.json` | One entry per article: `sourceId`, file, title, category, audience, tags. The publisher reads this. |
| `faqs.json` | FAQ pairs for `CrmKbFaqs`, each linked to an article by `sourceId`. |
| `*.md` | One article per file. Front matter + body. |

## Article contract (front matter)

```yaml
---
sourceId: setup-dashboard/customers-step     # CrmKbArticles.SourceId (unique, filtered index). Never renamed.
title: Customers: what each customer needs    # CrmKbArticles.Title (<= 200 chars)
category: Getting set up                      # CrmKbCategories.Name in the shipped layer; created if missing
audience: [admin]                             # CrmKbArticles.AudienceCsv (admin | dispatcher | driver)
tags: [customers, clients, invoice schedule]  # CrmKbArticles.TagsCsv (<= 500 chars). Include the old-system words.
---
```

Fixed on publish: `Layer = 'shipped'`, `IsManaged = 1`, `IsAutoGenerated = 0`, `Status = 'published'`,
`SourceVersion = <git commit of the file>`, `SourceDocumentUrl = <GitHub blob URL>`, `LastSyncedDateUtc = now`.
Body markdown becomes `ContentHtml`; the plain text of it becomes `ContentText` (what search runs over).

## Authoring rules, and why

These follow how CSP retrieves and uses an article today (`KeywordKbSearch.cs`, `ChatService.cs` on `develop`):

1. **Lead with the answer.** Ask Auto-Mate grounds each reply on the top 3 search hits and sends the model only the
   **first 400 characters** of each. If the answer isn't in the first paragraph, Auto-Mate never sees it.
2. **One question per article.** Search is keyword overlap with the title weighted 0.45, body 0.30, tags 0.15. A
   long "everything about rates" page loses to five short ones named after what people ask.
3. **Title = the question or the task**, in the words a tenant admin uses ("Why does my rate apply to every customer?").
4. **Tags carry synonyms**: US and NZ words (zip / post code, state / city), old-system words (client / customer /
   account, driver / courier / agent), and the field label as it appears on screen.
5. **Short.** 120–300 words. Reference tables (file columns) can be longer, but the first paragraph still answers.
6. **FAQs** are scored on question 0.55 + answer 0.35 and also truncated to 400 characters. Keep answers to 2–3 sentences
   and put the most-asked phrasing in the question.
7. **No tenant names, no DFRNT-internal detail** (table names, endpoints, gap numbers). Those belong in the design doc,
   not in a shipped article a tenant reads.
8. **Plain prose, no markdown tricks.** Auto-Mate answers in plain prose; headings and tables are for the Help Centre page.

## Publishing into CSP (not built yet)

The shipped layer is "DF-authored content delivered into the tenant DB" (`KbLayer.cs`): CSP's own API refuses to create
or edit shipped articles (`RequireAuthorableLayer`), and nothing feeds the layer today. CSP is per-tenant, so publishing
means a fan-out to every tenant database. Three ways to do it, in order of how soon each could run:

| | Mechanism | Pros | Cons |
|---|---|---|---|
| **A** | A generated SQL migration in `dbmigrationsv2` that `MERGE`s `CrmKbCategories` + `CrmKbArticles` + `CrmKbFaqs` by `SourceId` | Works now with zero CSP code; runs on every tenant with the next deploy; matches the "delivered by migration" wording in the code | Content changes become migrations; HTML in SQL; release-coupled |
| **B** | A CSP service endpoint `POST api/v1/knowledge-base/shipped/sync` keyed like Hub's `X-Api-Key` endpoints, body = manifest + articles; a GitHub Action in this repo calls it per tenant on merge to master | Content ships when docs change, not when code does; same path serves release notes (`dfrnt-release-notes` skill) and the how-to docs site | Needs CSP work (endpoint + key + tenant loop) |
| **C** | A `dfrnt-mcp` write tool `kb.publish_shipped` from the agent-access spec | Fits "the MCP and agents populate the knowledge base with every update" | Furthest away; needs Group 10 journaled writes first |

Recommendation: **B**, with **A** as the stop-gap if Auto-Mate help is wanted before the CSP endpoint exists. Either
way the upsert key is `SourceId`, so re-publishing updates in place and `IsHidden` set by a tenant survives.

The generator for A exists: `node docs/help/build-migration.mjs <out.sql>` renders every article to HTML + flattened text
and emits one idempotent `MERGE` per article (by `SourceId`) plus the category and FAQs, guarded on the KB tables
existing. Each content change is a NEW migration file (DbUp journals by filename). First one:
dbmigrationsv2 `DatabaseScripts/Migrations/20261026120000_SeedShippedKbSetupDashboardHelp.sql`
(branch `docs/seed-shipped-kb-setup-dashboard` on the GitHub mirror, dry-run twice on LocalDB 26 Oct 2026).

## Keeping it true

- The dashboard's step forms are the source of truth for required fields. If a `Validate` method in a pusher changes,
  search this folder for the field label and fix the article the same day.
- `faqs.json` answers must agree with the article they point at. If they can't both be short and true, fix the article.
- Kenneth's how-to site (`dfrnt-howto-docs`) covers the apps themselves (Settings, Routed Operations, Admin Manager).
  These articles stop where that site starts: they say *which* screen in Settings finishes a job, not how that screen works.
